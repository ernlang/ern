# Rapport — formalisation de MM-02 v0.3 (deuxième passe)

Modèle exploratoire. Ce rapport se lit sans ouvrir le Lean.

- Spécification : « ERN — Memory Model, v0.3 consolidée », non copiée dans le dépôt.
- Module : `formal/Ern/MM02.lean`, module `Ern.MM02`, namespace `Ern.MM02` (même fichier qu'en v0.2, mis à jour).
- Branche : `formal/memory_model_0.3`, créée depuis `formal/memory_model_0.2`, un commit par étape du prompt. Rien modifié hors `formal/`.
- Toolchain : Lean 4.35.0 (pinnée, inchangée), core uniquement, aucune dépendance.
- `lake build` passe sans avertissement. Aucun `sorry`, `admit`, `axiom`, `native_decide`.
- 30 théorèmes, tous prouvés, plus un `example` de non-vacuité. `#print axioms` : au plus `propext`, `Quot.sound`, `Classical.choice`. `Classical.choice` n'apparaît que dans les théorèmes qui mentionnent une opération brute ou vérifiée, parce que celles-ci décident leur précondition classiquement (voir (c) 4).

## Le modèle en bref

- **État** : une fonction `identité ↦ allocation ou rien` et un compteur `next`, prochaine identité fraîche. Deux invariants côte à côte : `WF` (toute identité `≥ next` est inutilisée) et `LiveDisjoint`.
- **Allocation** : espace d'adressage, base, étendue, alignement, état vivant/mort, octets (fonction `décalage ↦ octet abstrait`), jeton de désallocation optionnel.
- **Octet abstrait** : non initialisé, ou initialisé avec une valeur sur 8 bits (`UInt8`) et une provenance optionnelle.
- **Emplacement** (`Place`) : identité d'allocation, décalage, longueur. **Moyen d'accès** (`Access`) : adresse, provenance, longueur, autorité `read ≤ write`. **Résolution** `Access.toPlace` : partielle, par la provenance.
- **Trois niveaux, séparés comme le demande MM-02.H** :
  - préconditions : `Read`, `CanWrite` (et leurs formes par résolution `ReadPlace`, `CanWritePlace`), `CanDealloc`, `AllocPre` ;
  - effet d'une opération valide : fonctions totales `State.write`, `State.dealloc`, `State.alloc` (la lecture n'a pas d'effet) ;
  - issue observable : opérations brutes `read`, `write`, `dealloc`, `alloc`, de résultat `Outcome` (`ok` avec le nouvel état, ou `ub`) ; variantes vérifiées `checkedWrite`, `checkedDealloc`, de résultat `Outcome'` (`ok`, `ub` ou `fail`).
- **Obligations non décidées par le noyau** (type, alignement des accès, concurrence) : paramètres explicites et opaques `ObR` de `read` et `ObW` de `write` et `checkedWrite`. Une opération brute rend `ok` seulement si la précondition du noyau **et** ce paramètre sont satisfaits.

### Théorèmes nouveaux, en une phrase chacun

- `LiveDisjoint.of_fields` : un pas qui ne rend vivante aucune allocation et conserve espace, base et étendue de toute allocation restée vivante préserve `LiveDisjoint`.
- `liveDisjoint_write`, `liveDisjoint_dealloc` : l'effet d'une écriture, d'une désallocation, préserve `LiveDisjoint`, sans hypothèse sur l'écriture ou la désallocation.
- `liveDisjoint_alloc` : l'effet d'une allocation dont `AllocPre` est satisfaite préserve `LiveDisjoint`.
- `toPlace_eq_some` : la résolution rend `p` ssi la provenance désigne une allocation existante `a`, l'accès est spatialement contenu dans `a`, et `p` est la portion désignée.
- `read_iff_place`, `canWrite_iff_place` : `Read` équivaut à `ReadPlace`, `CanWrite` à `CanWritePlace`.
- `dealloc_eq_ok`, `alloc_eq_ok` : l'opération brute rend `ok s'` ssi sa précondition est satisfaite et `s'` est l'effet.
- `checkedWrite_ne_ub`, `checkedDealloc_ne_ub` : une variante vérifiée ne rend jamais `ub`, pour toute valeur des paramètres `ObW` et `Compatible`.
- `dealloc_invalidates` (P2a) : si la désallocation brute de l'allocation visée par `ac` rend `ok s'`, alors dans `s'` toute lecture et toute écriture brutes par `ac` rendent `ub`.
- `no_double_free` (P2c) : si la désallocation brute de `id` rend `ok s'`, alors dans `s'` une nouvelle désallocation brute de `id`, avec toute autorité, rend `ub`.
- `reuse_does_not_restore` (P2b) : si la désallocation brute de l'allocation visée par `ac` rend `ok s₁`, puis une allocation brute d'espace, base, étendue, alignement et jeton **quelconques** rend `ok s₂`, alors dans `s₂` toute lecture et toute écriture brutes par `ac` rendent `ub`. La base est un argument universellement quantifié ; l'exemple 1 montre qu'elle peut être celle de l'ancienne allocation.
- `write_frame` : l'effet d'écriture laisse inchangées les autres allocations ; dans l'allocation visée, seuls les octets changent, et ceux hors de la plage écrite sont inchangés ; `next` est inchangé.
- `dealloc_frame` : l'effet de désallocation laisse inchangées les autres allocations et `next`.
- `alloc_frame` : si l'identité `next` est fraîche, l'effet d'allocation laisse inchangée toute allocation existante.
- Exemple 1 (`example`) : allocation dans un état vide, désallocation, puis nouvelle allocation à la même base ; les trois opérations brutes rendent `ok`.

## (b) Règles abstraites

Le noyau v0.3 ne décide pas ces conditions. Conformément à la phrase de portée de la spec, elles ne sont ni omises ni remplacées par `True` : chacune est un **paramètre explicite et opaque** des opérations brutes.

- **MM-02.B.4, B.6, B.7** (représentation valide pour le type lu, alignement du type lu, concurrence) : `ObR : State → Access → Prop`, argument de `read`.
- **MM-02.C.4, C.5, C.6** (valeur admissible, alignement, concurrence) : `ObW : State → Access → (Nat → UInt8 × Option Nat) → Prop`, argument de `write` et de `checkedWrite`.
- **MM-02.D** compatibilité d'autorité : relation paramétrique `Compatible : Nat → Nat → Prop`.

Les prédicats du noyau `Read` et `CanWrite` restent ceux de v0.2 et ne contiennent pas ces conditions. Les théorèmes valent pour **toute** valeur de `ObR`, `ObW` et `Compatible` : aucun n'affirme qu'une de ces conditions est satisfaite. Instancier `ObR` et `ObW` par `True` redonne exactement le traitement par omission de v0.2.

Propriétés non représentées (obligation 8 de la spec) :

- typage : B.4, C.4 dans `ObR`/`ObW`, sans contenu ;
- alignement des accès typés : B.6, C.5 dans `ObR`/`ObW` ; seul l'alignement des **allocations** est modélisé (`AllocPre`) ;
- concurrence : B.7, C.6 dans `ObR`/`ObW` ; MM-02.F hors périmètre, aucun contexte d'exécution dans l'état ;
- permissions temporelles et fines : aucune ; l'autorité d'accès est fixe dans `Access` ;
- conversions d'adresses : MM-02.G hors périmètre ; aucune opération ne forme un accès depuis un entier ;
- autres données de validité d'un moyen d'accès (MM-02.5) : omises.

## (c) Décisions de modélisation non dictées par le texte

1. **Obligations non décidées : paramètres explicites, pas omission.** « Les exigences de typage, d'alignement des accès, de concurrence et de permissions fines qui dépendent de spécifications futures restent des obligations d'interface explicites ; elles ne doivent pas être silencieusement remplacées par `True` puis considérées comme prouvées. » Le prompt demande d'abstraire « comme en v0.2 », c'est-à-dire par omission, l'alignement des accès (B.6/C.5) et la concurrence ; il ne dit rien du typage (B.4/C.4), lui aussi omis en v0.2. Avec des issues, l'omission ferait rendre `ok` à une lecture brute mal alignée, alors que la spec en fait un UB. Les paramètres `ObR`, `ObW` évitent cette contradiction et contiennent l'omission comme cas particulier. Voir (e) 1.
2. **`Outcome.ok` porte l'état, pas la valeur lue.** « lorsqu'elle doit fournir une valeur, cette valeur fait partie du résultat conceptuel. » Le prompt fixe `Outcome | ok (s : State) | ub` ; la spec dit que « la manière de représenter le résultat d'une lecture » est un choix de formalisation. La valeur lue est déterminée par les octets de l'état aux positions désignées, mais aucune fonction ne la rend. Voir (e) 2.
3. **Fonctions d'effet séparées des opérations brutes.** « Il faut séparer préconditions, effet d'une opération valide et issue observable. » Les effets `State.write`, `State.dealloc`, `State.alloc` sont totaux ; hors précondition ils ne servent qu'à énoncer des lemmes. Seules les opérations brutes donnent la sémantique, et elles rendent `ub` hors précondition (« elle n'a pas un effet « arbitraire mais valide » pouvant être réutilisé comme un pas ordinaire du modèle »). Les lemmes `write_frame`, `dealloc_frame`, `liveDisjoint_write`, `liveDisjoint_dealloc` portent sur l'effet pour tous les arguments, ce qui est plus fort que sur l'issue `ok` ; `alloc_frame` porte sur l'effet sous la seule clause de fraîcheur de `AllocPre` ; `liveDisjoint_alloc` suppose `AllocPre` entière, dont seule la clause de non-chevauchement sert.
4. **Décision classique dans les opérations brutes et vérifiées.** « Les conditions de sûreté peuvent être établies statiquement, vérifiées dynamiquement avant l'opération dangereuse ou garanties par les invariants d'une abstraction sûre correctement implémentée. » Les préconditions contiennent des paramètres opaques et des quantifications non bornées : le `if` est décidé classiquement, et ces définitions sont `noncomputable`. Une vérification dynamique réelle exige des obligations décidables ; le modèle ne dit pas comment elles le sont.
5. **`LiveDisjoint` à côté de `WF`, pas dedans.** « Deux allocations abstraites vivantes, distinctes, dans le même espace d'adressage, occupent des plages d'adresses disjointes. » L'inclure dans `WF` aurait obligé `alloc_wf` à supposer `AllocPre`, donc affaibli un énoncé v0.2.
6. **Disjonction comme intersection vide, quantifiée sur les adresses.** « Deux plages disjointes ont une intersection vide. Une plage de taille nulle ne chevauche donc aucune autre plage. » `RangeDisjoint b1 n1 b2 n2` dit qu'aucune adresse n'est dans les deux plages semi-ouvertes. Le choix porte sur la forme (quantification sur les adresses). Sa conséquence, une allocation de taille nulle créable à toute base alignée, même à l'intérieur d'une allocation vivante du même espace, est dictée par le texte.
7. **Puissance de deux : `∃ k, n = 2 ^ k` ; `0 < align` gardé explicitement.** « un alignement strictement positif, puissance de deux, auquel sa base satisfait ». La positivité découle de la puissance de deux ; la clause est gardée pour suivre le texte.
8. **Alignement valide exigé à la création, pas énoncé comme invariant.** Même phrase. Toute allocation créée par l'opération brute `alloc` le satisfait, et ni l'écriture ni la désallocation ne changent base ou alignement. Mais aucun invariant d'état ne le dit, et l'effet `State.alloc` seul accepte tout alignement. Voir (e) 3.
9. **Fraîcheur : `s.allocs s.next = none`.** « Dans le noyau exploratoire, la création d'une allocation vivante exige la fraîcheur de son identité, un alignement valide, une base correctement alignée et le respect de `LiveDisjoint`. » L'identité est choisie par la machine (`next`) ; la fraîcheur est celle de cette identité. Sous `WF` elle est toujours vraie ; elle ne peut échouer que dans un état qui viole `WF`. Comme une allocation morte reste enregistrée, une identité déjà utilisée n'est jamais fraîche. Le prompt ne liste pas la fraîcheur parmi les préconditions de `alloc` (« non-chevauchement, `align > 0` puissance de deux, `base % align = 0` ») ; elle est ajoutée parce que la spec l'exige, en MM-02.2 et dans l'obligation 3 (« Ajouter les préconditions de création : fraîcheur, alignement strictement positif puissance de deux, base alignée, non-chevauchement. »). `reuse_does_not_restore` en dépend.
10. **Non-chevauchement vérifié contre les seules allocations vivantes du même espace.** « Une même adresse numérique peut être réemployée après libération du stockage précédent. » Une allocation morte n'occupe plus de plage ; l'exemple 1 réutilise exactement la même base.
11. **`Access.toPlace` résout aussi une allocation morte.** « un moyen d'accès ne produit un emplacement que si la provenance identifie une allocation existante et si la plage d'adresses est spatialement incluse dans celle-ci. » « Existante » est lu comme « enregistrée » ; la vivacité est vérifiée séparément (« vivacité, initialisation, autorité, type, alignement et concurrence sont vérifiés séparément »).
12. **`ReadPlace` et `CanWritePlace` ajoutés à côté de `Read` et `CanWrite`**, avec leur équivalence. « Produire un emplacement résolu ne prouve pas, à lui seul, le droit de lire ou écrire ». Les opérations brutes utilisent `Read` et `CanWrite` ; par l'équivalence, le choix ne change rien.
13. **L'appelant choisit la base de l'allocation**, argument de `alloc`. « La réservation effective de ressources peut en plus échouer de manière définie ; ce cas n'est pas confondu avec la violation des préconditions d'une opération brute. » Le choix d'adresse de l'allocateur et son échec défini ne sont pas modélisés ; une base invalide donne `ub`, jamais un échec défini.
14. **`Outcome'.fail` ne porte pas d'état.** « Lorsque le contrôle échoue, elle produit un échec défini (`fail`, ici terme abstrait) sans provoquer `ub`. » L'état après un échec défini n'est pas représenté ; il est implicitement inchangé.
15. **Une variante vérifiée contrôle exactement la précondition de l'opération brute, paramètres compris, puis l'appelle.** « Une variante sûre vérifiée contrôle les obligations avant d'appeler l'opération brute. » `checkedWrite` contrôle `CanWrite` et `ObW` ; un contrôle plus faible rendrait `checkedWrite_ne_ub` faux.
16. **`write_frame` dit « seuls les octets changent » sous la forme `{ a' with bytes := a.bytes } = a`.** « Les octets des autres allocations et les octets extérieurs à la plage d'écriture dans l'allocation visée sont inchangés ; l'identité et le compteur d'allocation ne sont pas affectés. » Le décalage de la plage est `addr - base`, soustraction tronquée.
17. **`no_double_free` quantifie sur toute seconde autorité.** « Une tentative de double désallocation par l'opération brute viole une obligation de sûreté et constitue un UB. »
18. **Valeur d'octet `UInt8`**, plutôt que `Fin 256`. « Le noyau v0.3 considère des octets de 8 bits, dont la valeur initialisée est comprise entre 0 et 255. » Aucune arithmétique sur les valeurs n'est faite ; les deux conviennent.
19. **Un moyen d'accès ne porte pas d'espace d'adressage.** « La résolution se fait par la provenance, jamais en choisissant simplement une allocation à l'adresse numérique demandée. » L'espace est celui de l'allocation résolue ; la validité spatiale compare des adresses à l'intérieur de cette allocation.
20. **Exemple 1 de la spec comme témoin de non-vacuité**, avec `Compatible` instancié par la relation toujours vraie dans cet exemple seulement. « allocation `A`, libération de `A`, puis allocation `B` à la même adresse ».

Décisions reprises de v0.2, toujours en vigueur :

21. **Identité = clé de la fonction `identité ↦ Option Alloc`.** « une identité unique dans l'exécution abstraite ».
22. **Une allocation morte reste enregistrée, octets conservés.** « Une allocation morte peut rester enregistrée à des fins de raisonnement sans redevenir vivante. »
23. **Octets : fonction totale sur les décalages.** « un stockage abstrait indexable par décalage, constitué d'octets abstraits ». Les indices au-delà de l'étendue existent mais aucune lecture permise ne les consulte.
24. **Validité spatiale : inclusion semi-ouverte**, désormais définie par la spec (« `b ≤ a` et `a + n ≤ b + s` »). Soustraction tronquée `addr - base` pour obtenir un décalage, significative seulement sous cette condition.
25. **B.3 : tous les octets de la plage.** « les octets requis pour la représentation lue sont initialisés ». Sans type, la représentation requise est la plage entière.
26. **Ordre `a ≤ b` ssi `a = read` ou `b = write`.** « L'autorité de lecture/écriture du modèle exploratoire est ordonnée `read ≤ write` ».
27. **`freeAuth : Option Nat`, jeton relié aux autorités capables par `Compatible`.** « Cette compatibilité est une relation sémantique ; elle n'exige pas nécessairement l'identité numérique des deux handles d'allocateur, et elle est distincte de la provenance d'accès. »
28. **`Derive` est une relation entre deux accès, pas une opération.** « la création de droits ne se réduit pas à une dérivation restrictive ».
29. **Contenu écrit arbitraire, la provenance écrite vient de lui.** « La provenance stockée provient de la valeur et de sa représentation écrites, et non automatiquement de la provenance du moyen d'accès ayant servi à l'écriture. »

## (d) Théorèmes non prouvés

Aucun. Remarques :

- `read_requires_live`, `derive_prov`, `derive_auth_le` restent des projections directes des définitions.
- `dealloc_invalidates`, `no_double_free` et `reuse_does_not_restore` (issues) supposent une désallocation brute réussie : une désallocation qui échoue rend `ub` et ne produit pas d'état sur lequel raisonner. Les formes `_pre` gardent les énoncés v0.2, sans hypothèse de désallocation réussie ; `reuse_does_not_restore_pre` garde `WF` et l'existence de l'allocation, comme en v0.2.
- `reuse_does_not_restore` tient grâce à la précondition de fraîcheur de l'allocation brute : l'ancienne allocation, morte mais enregistrée, rend son identité non fraîche. Sa preuve n'utilise pas la base.
- `checkedWrite_ne_ub` et `checkedDealloc_ne_ub` tiennent parce que le contrôle est exactement la précondition de l'opération brute.
- Les branches `ok` de `read`, `write` et des variantes vérifiées ne sont fixées que par leurs définitions : seules `dealloc` et `alloc` ont un lemme `*_eq_ok`. Les énoncés de `dealloc_invalidates`, `reuse_does_not_restore` et `checkedWrite_ne_ub` resteraient vrais pour une lecture ou une écriture brute qui rendrait toujours `ub`, ou pour une variante vérifiée qui rendrait toujours `fail`.
- B.5 (« l'autorité de lecture est valide ») reste toujours vraie avec les seules autorités `read` et `write`.

## (e) Questions pour arbitrage

1. **Obligations non décidées : paramètres ou omission ?** Le prompt dit « comme en v0.2 » (omission) ; la phrase de portée de la spec interdit de les remplacer silencieusement par `True`, et avec des issues l'omission ferait rendre `ok` à des opérations que la spec classe UB. Le modèle les prend en paramètres (voir (c) 1). À confirmer.
2. **Valeur rendue par la lecture.** MM-02.H dit que la valeur fait partie du résultat conceptuel ; le type imposé par le prompt ne la porte pas. Faut-il `Outcome` paramétré par un type de résultat, ou une fonction de lecture séparée ?
3. **Alignement valide comme invariant.** MM-02.2 le donne comme propriété de toute allocation ; le modèle ne l'exige qu'à la création. Faut-il un invariant d'état, avec ses théorèmes de préservation ?
4. **Lecture vérifiée.** MM-02.B demande qu'« Une interface de lecture sûre doit établir la condition ou signaler un échec défini avant l'opération dangereuse » ; le prompt ne demande que `checkedWrite` et `checkedDealloc`. Faut-il `checkedRead` ?
5. **État après `fail`.** `Outcome'.fail` ne porte pas d'état. Faut-il le rendre explicite (inchangé) ?
6. **Échec de fraîcheur.** La spec exige la fraîcheur à la création ; l'identité étant choisie par la machine (`next`), elle ne peut échouer que dans un état qui viole `WF`. Un tel échec doit-il être un `ub` de l'allocation brute, comme dans le modèle, ou faut-il faire de `WF` une hypothèse globale de la sémantique ?
7. **Autorité de lecture.** B.5 ne filtre toujours rien ; la spec prévoit qu'« Une autorité peut ultérieurement dépendre de l'état et être invalidée ». Rien à faire en v0.3 ?
8. **« Allocation existante » dans la résolution.** Lu comme « enregistrée, vivante ou morte » (voir (c) 11). À confirmer.
9. **Échec défini de réservation.** L'allocation brute ne peut pas échouer de manière définie. Faut-il une variante d'allocation à issue `fail` dès cette passe, ou attendre le contrat de l'allocateur ?

## (f) Conflits avec `formal/DESIGN.md`

Aucune exigence du prompt ne contredit `formal/DESIGN.md` au point d'imposer un écart ; rien n'a été fait contre DESIGN.md. Tensions à arbitrer :

1. **Deux notions d'emplacement.** DESIGN.md : « Abstract model. Memory is a set of places: variables and field paths ». Le `Place` de ce module est celui de MM-02.4 (identité, décalage, longueur), une notion du modèle *concret*. Le nom est le même, la notion non.
2. **Ordre de construction.** DESIGN.md place le modèle concret (« Concrete model, layout interface and refinement ») au jalon 3, après le flot de contrôle et le modèle abstrait. Ce module est un fragment exploratoire du modèle concret, construit avant son tour à la demande des prompts, sans interface de layout (aucun type dans le périmètre). Il ne décide rien pour le jalon 3.
3. **Comportements observables.** DESIGN.md définit au niveau du programme « termination with its observable result, trap, undefined behavior, divergence ». `Outcome` et `Outcome'` sont des issues par opération ; `fail` est un échec défini qui peut être une valeur d'erreur, pas forcément un « trap ». La projection des issues d'opération sur les comportements de programme reste à définir.
4. **Interpréteurs.** DESIGN.md : « Interpreters for tests iterate steps with fuel. » Les opérations brutes et vérifiées sont `noncomputable` (décision classique, voir (c) 4) ; un interpréteur exigera des instances de décision pour `Compatible`, `ObR`, `ObW`, `AllocPre`, et aussi pour `Read` et `CanWrite` (égalité décidable sur `AByte`, décision de `≤` sur `Auth`), absentes du module.
